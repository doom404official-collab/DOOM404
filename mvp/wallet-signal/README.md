# DOOM404 Wallet Signal

Version: v0.1

DOOM404 Wallet Signal is an experimental Solana wallet analytics prototype.

## MVP

Input:
- Public Solana wallet address

Analysis:
- Latest 100 transactions
- Basic wallet/account information

Signals:
- Activity
- Diversification
- Trading
- Maturity

## Principles

- Explainable signals
- Public blockchain data only
- No wallet connection required
- No private keys
- No transaction signing
- No smart contract required
- No "safe", "scam", or investment verdicts

## Status

MVP development started.

### LQ-13 historical continuation/interruption preparation

The historical investigator now requires an explicit valid source, retained counters/coverage flags and a nonempty continuation cursor/history. Missing or incompatible legacy input fails before provider work; no default empty scan is created and absent counters are not fabricated. The source file is never overwritten. Output must be a new distinct path; existing output or an outstanding local lock requires reconciliation. This deliberately makes the legacy workflow's missing-source fallback fail closed; no workflow activation or schedule was changed.

Request count limits, 20-second request timeout, retry count and primary/fallback accounting remain unchanged. An additional provider-work deadline is at most eight minutes (`GLITCH_HISTORY_DURATION_MS` may only shorten it); request/body parsing and retry sleeps share that deadline. SIGTERM/SIGINT or a timed-out operation stops further dispatch, including fallback. Redirects cannot create uncounted hops. This runtime deadline is not proof of remaining GitHub job time after dependency installation: orchestration must supply a reviewed shorter limit when needed. SIGKILL and machine/storage loss remain outside graceful-cancellation guarantees.

The CLI writes a full in-progress checkpoint before transport and after every newly validated transaction, before another paid lookup. Completed page cursor/count advancement is saved with its final validated entry. Prior signature prefix, events, errors and provenance remain intact; failures take precedence over request-budget stop reporting. In-progress output reuses existing `RETRIEVAL_INCOMPLETE`, `complete: false` and `historyCoverageVerified: false`; it is not an automatically promotable successor. An explicitly reviewed partial source can still be examined by the CLI, as before, while automatic gates remain paused. No checkpoint schema version, artifact name, numeric score or authorization flag is promoted.

Local persistence uses exclusive `.lock`, exclusive `.pending`, flushed file content and atomic rename to the existing output filename. Each publication is bounded to 20 seconds; a timeout/failure prevents subsequent publication attempts and preserves the last whole output plus any pending file/lock. Late writes cannot initiate a rename after timeout. A rename may nevertheless have completed before its error response: a failed run must remain quarantined even if its JSON looks valid. Reconcile the run result and all files independently before successor acceptance; do not treat file existence as success. Power-loss durability and distributed CAS are not established. Filesystem failure can prevent saving the latest in-memory observation; the CLI stops instead of spending more requests or claiming it persisted.

Existing workflows upload only the original output, not the `.pending`/`.lock` sidecars. Their upload/retention and failed-run admission contract therefore needs an explicit reviewed integration proposal before live activation; no artifact identity was silently expanded. The minimum next safe proposal is shared distributed fencing plus atomic successor/receipt publication and failed-run quarantine across investigator/replay/other writers, with compatibility, quiescence and rollback specified. Hosted schema/grants or workflow activation require separate approval. The separate replay CLI's end-only persistence remains a distinct uncompleted integration boundary; this slice does not claim it was hardened.

### LQ-13 replay preservation and proposed shared admission contract

Replay now uses the reviewed local deadline/publisher for incremental diagnostic preservation. It requires the original checkpoint and exact existing source-digest plan, rejects duplicate plan signatures and source/plan/output aliases, and has no automatic partial-output resume input. A separately reviewed plan may explicitly select remaining signatures from the unchanged original source. Existing source schema, digest definition, replay kind and artifact name remain unchanged. `REPLAY_BATCH_COMPLETE` describes only that replay batch, never an accepted historical checkpoint, authorization proof or score input. In-progress output is `PARTIAL_UNRESOLVED`. Timing is capped by the same eight-minute maximum and 20-second operation ceiling, with the existing request budget unchanged. No workflow wiring changed.

The local publisher rechecks output and pending-file existence after taking its exclusive lock. This closes the demonstrated cooperating-writer race where another process published between the first check and lock acquisition. Stale locks/pending files are not reclaimed; source symlink/hardlink collisions fail before transport. Prior uncertain-rename/late-write tests still apply. A local lock cannot constrain another machine, a non-cooperating process that edits/removes lock files, filesystem administrator actions or an external writer. Distributed and power-loss guarantees are not claimed.

**Proposed design, not deployed or approved:** one shared Liquidity execution lease would cover investigator, replay and stage-1 writers instead of the current separate Actions groups. An immutable operation manifest must bind reviewed repository/ref/commit, run/attempt, purpose, source artifact identity and full-byte digest, legacy semantic source digest, pool/mint scope, exact approved request ceiling and absolute window. Claims must atomically advance a fencing epoch, reject an active lease including same-owner reclaim, and never automatically extend the approved window. Every reservation/mutation must compare the live epoch and expiry using database time. Attempt reservations and observed paid requests remain distinct ledger fields; uncertain reservations stop work rather than resetting budgets or claiming dispatch.

Artifacts must first be staged as quarantined immutable evidence. Receipts must distinguish artifact/run status, digest, lineage validation and publication uncertainty; valid JSON alone cannot admit a failed or unknown run. Replay remains diagnostic. A separately reviewed history candidate may advance the canonical tip only through one database transaction comparing current tip/epoch/window, verifying the independently reconciled artifact receipt, and appending the terminal admission receipt atomically. Lost acknowledgement requires read-only reconciliation by immutable operation ID, not mutation retry. Artifact staging and database commit are not one cross-service transaction, so orphan/unadmitted artifacts remain quarantined without automatic deletion. Full-byte hashes supplement rather than redefine the legacy semantic digest or rewrite history.

Executable proposal tests model competing claims, same-owner reclaim rejection, expired epochs, reservation caps, stale parent/digest, failed-run/replay quarantine, atomic receipt/tip transition and lost-acknowledgement readback. These specify desired transactions only; they are not SQL concurrency or authentication proof. No migration, table, login, grant, environment flag or hosted adapter is introduced.

Missing/expired bindings fail closed.

### LQ-13 disposable SQL candidate — repository assumptions only

The unapplied [disposable fencing candidate](docs/proposals/liquidity-fencing-disposable.sql) and [local runner](tests/fixtures/liquidity-fencing/run-local.py) make the reviewed transaction model executable. The SQL rejects every database/user except the named disposable fixture, creates no enrolled tip or manifest, changes no public table, grants no runtime access and is deliberately outside migrations/active workflows. It is **not a migration asserted compatible with GLITCH hosted state**. The runner uses the already-present `postgres:17` image with networking disabled, no published ports and no production credentials; it removes only its own container.

The candidate has one explicitly enrolled pool/tip and one shared execution lane, monotonic bigint fencing, one-time operation claims, per-operation reservation ordinals, quarantined immutable artifact records, separate trusted reviews, and append-only admission receipts. All critical reads use row locks; wall-clock expiry is rechecked after locks. Same-owner reclaim and replayed reservations fail. Receipt insertion and canonical-tip advancement are one transaction. The review must match artifact ID/digest, parent, repository manifest commit/run/attempt and successful independent lineage/publication reconciliation. Replay and stage-1 observations cannot become historical tips. Full artifact hashing and caller authentication are external prerequisites, not proved by a stored digest or boolean.
